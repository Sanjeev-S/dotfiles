# DGX Spark runs on Ethernet; Wi-Fi is a fallback, not the primary link

The Spark's MediaTek MT7925 Wi-Fi firmware crashes and silently resets roughly twice a day on 6GHz WPA3 with Wi-Fi 7 MLO — a known upstream defect with an NVIDIA bug open as of 2026-08 and no vendor fix. The crash alone would be survivable, but NetworkManager 1.46 converts it into a multi-day outage: the chip re-associates to a WPA2 BSS, the 4-way handshake fails, NM classifies *any* handshake failure as a wrong password, re-requests secrets with a flag that bypasses the stored PSK, and — finding no secret agent, because those live in graphical sessions — sets a sticky `NO_SECRETS` autoconnect block that only a reboot clears. It stranded the box four times in 60 days, up to 2.7 days each, every time needing a physical power cycle.

Five ways out were considered: (a) a systemd watchdog running `nmcli networking off/on`, which provably clears the block but leaves the box crashing underneath and recovering on a timer; (b) moving the link off NetworkManager to wpa_supplicant or systemd-networkd, whose backoff ladder retries forever by design and needs no agent — structurally correct, but a mis-staged change strands a headless box with no link at all; (c) out-of-tree mt76 patches that fix the crash itself, at the price of a DKMS rebuild on every kernel update, where one failed rebuild is again a stranded box; (d) pinning the client off 6GHz to dodge the MLO code path, which trades throughput for a trigger the firmware may hit elsewhere; (e) Ethernet.

Chose **(e) Ethernet**, at 10GbE. It is the only option that removes the *dependency* rather than managing the failure: no association, no handshake, no secrets, so the entire class is impossible. The Wi-Fi profile stays configured at a higher route metric, which costs nothing and means the box self-heals onto Wi-Fi if the cable is ever pulled. Trade-off accepted: the Spark must live within reach of a cable drop. Note also that a previous attempt at a software fix — a `conf.d` drop-in setting `autoconnect-retries=0` — was a no-op twice over: the bare key is invalid in `[connection]` (NM logs "unknown key" and ignores the file), and retry counts do not clear a `NO_SECRETS` block. Do not reintroduce it.

**Revisit if** NVIDIA ships a firmware fix or DGX OS moves to a kernel carrying the mt76 MLO fixes, or the box has to live somewhere without a cable — in which case (a) is the fallback, and (b) is the durable answer if Wi-Fi must ever be the primary link again.
